Check-out read `priorInvoice` **before** opening its transaction, because the invoice number has to be minted outside one, and then branched on that read hundreds of milliseconds later — after claiming the booking, recording the payment and pricing the stay. A draft committing in between sent it down the `create` branch against a row that now existed: unique violation on `bookingId`, the whole transaction rolled back, HTTP 500. The guest is checked in, the bill is **not** frozen, the room is not sent to cleaning, and the desk is looking at a server error on somebody standing at the counter. **Not theoretical:** three CI runs failed on it — `42926638007` and `42963870848` on `dev` with nothing related in flight, and `43138525842` on a branch — surfacing in whichever test happened to book and check out fast enough (`room-detail-overstay.test.ts`, then `room-status-occupied-guard.test.ts`, then the first again), each with `Unique constraint failed on the fields: (bookingId)`. **Three fixes were weighed and two rejected on their merits.** Catching the P2002 and falling back to the update cannot work: in Postgres a failed statement poisons the whole transaction, so the fallback would itself fail with `25P02`, and Prisma exposes no savepoint to roll back to. Re-reading inside the transaction narrows the window and does not close it — under READ COMMITTED another insert can still land between the read and the write two statements later, and an insert that has not committed yet is invisible to the read however late it is taken. (An `upsert` was already out, for the reason the handler documents: Prisma validates the `create` branch even when it takes `update`, so the number reserved only for the create path would reject every check-out that has a draft, which is nearly all of them.) **So the two writers are serialised instead**, the same way the plan ceilings above are: a per-booking `pg_advisory_xact_lock` in `utils/invoice-lock.ts`, taken by `autoCreateInvoice` and by check-out, with the decision re-read under it. Whoever holds it does its read-and-write as one step; the other waits and then reads a world that already has the invoice in it. The lock is taken **late** in the check-out transaction, after pricing, so freezing a bill never keeps a background draft queued behind work it does not depend on; and it is per booking, so two bookings never wait for each other. Both call sites are load-bearing, and **each was mutation-tested separately**: reverting the re-read fails 4 of the 6 new tests, dropping either `lockBookingInvoice` call fails exactly 1 — the one written for that side. The lock ordering is exercised rather than argued: the test holds the invoice lock while check-out has already updated the booking row, and the draft's foreign-key check on that row still goes through, because `FOR KEY SHARE` does not conflict with the `FOR NO KEY UPDATE` a non-key update takes. If it did, the two would deadlock and the test would say so. `autoCreateInvoice` is exported now because the routes fire and forget it, so a test has nothing to await otherwise. **Stated rather than implied, three limits.** The two invoice routes that can also attach an invoice to a booking by hand (`POST /api/invoices` and `POST /api/invoices/booking/:id`, neither in a transaction) do **not** take the lock and can still lose the same way — a separate, unobserved race left alone rather than quietly half-fixed. The two serialisation tests watch for 300ms and assert the other writer has not moved, which can only pass falsely if an unlocked writer were slower than that; a local insert is about a millisecond. And one path is reasoned, not reproduced: if the invoice seen before the transaction were detached from the booking during it, there would be no number left to create one with — nothing does that during a check-out, so it now answers a truthful 409 asking the desk to retry instead of failing on a null. Covered by `checkout-invoice-race.test.ts` (6 tests; the 3 that reproduce the original window do so deterministically, by inserting the draft at the instant the handler's transaction opens — after the read, before the write — which is why it had been a flake nobody could pin down). Verified: the full API suite is **1339 passing across 108 files**, and `tsc --noEmit` on `apps/api` reports **0 errors**. No schema change |
